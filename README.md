### 2차 - 연결 유지

연결을 유지한 상태로 여러 메세지를 주고받고, 서로 연결을 종료시키는 방법에 대해 공부함\
따라서 [[Server/Sample1.cs]]에서 연결을 유지한 상태로 최대 메세지 전송 횟수를 넘거나 연결이 끊길 때까지 메세지를 주고 받도록 변경했고,\
[[Client/Sample1.cs]] 또한 동일하게 여러 메세지를 주고받을 수 있도록 함\
하지만 클라이언트 측은 메세지의 수신과 송신을 따로 분리해야 원할한 통신이 가능하다는 것을 깨닫고 [[Client/Sample2.cs]] 제작을 시작함\

두 Task가 연결 상태를 공유하기 위해 CancellationTokenSource에 대해 공부함

[[Client/Sample2.cs]]와 [[Server/Sample2.cs]]를 점검하면서 여러 비동기 작업이 하나의 `Dictionary`와 `StreamWriter`에 동시에 접근할 수 있고, 연결 자원의 생성과 정리 위치도 명확하지 않다는 것을 알게 됨

[[Server/Sample3.cs]]에서는 클라이언트 목록을 `ConcurrentDictionary`로 변경해 접속과 종료, 방송이 동시에 일어날 때 발생할 수 있는 동시성 문제를 보완함.

또한 각 `ClientInfo`가 bounded `Channel<string>` 형태의 송신 큐와 전용 송신 Task를 갖도록 변경함\
다른 작업들은 `StreamWriter`에 직접 쓰지 않고 `SendAsync()`를 통해 메세지를 큐에 넣으며, 실제 송신은 전용 Task가 순서대로 처리하도록 만들었음.

`ClientInfo`가 `TcpClient`, `Stream`, reader, writer를 직접 소유하고 `IAsyncDisposable`을 구현하게 하여 연결 자원의 생성과 정리도 한곳에서 담당하도록 변경함.

서버에서는 명령어 처리를 `CommandManager()`로 분리하고 `/stop` 명령어를 추가함\
서버 전체가 하나의 `CancellationTokenSource`를 공유하게 하여 `/stop`이 입력되면 accept, 송신, 수신 작업에 종료 신호가 전달되도록 함\
접속한 클라이언트에게 자신의 번호도 알려주도록 보완함

[[Client/Sample3.cs]]에서는 연결 자원을 `ClientInfo`로 분리하고, 포트 범위와 빈 메세지 같은 사용자 입력을 검증하도록 변경함\
송신과 수신 Task가 같은 취소 토큰을 공유하게 하고, 한쪽 작업이 끝나면 나머지 작업과 연결 자원도 함께 정리되도록 종료 흐름을 수정함.

이번 보완을 통해 여러 비동기 작업이 공유 자원에 접근할 때는 단순히 Task를 나누는 것뿐 아니라, 동시성 제어와 자원 소유권, 취소 및 종료 흐름까지 함께 설계해야 한다는 것을 공부함.\

### 4차 - 패킷 검증

본격적인 바이트 기반 TCP 통신으로 들어가기 전 패킷 생성과 해석 방법을 경험해봄

바로 전 학기에 배웠던 TCP 패킷을 기반으로 어떻게 패킷을 만들어야 할지 구상해봤고,\
어떻게 객체 형태의 패킷을 byte 배열로 만들지, 어떻게 byte 배열을 패킷 객체로 만들지에 대해 공부함

현재 패킷은 아래와 같이 구성됨

\[MagicByte(1byte)\]\[Payload 길이 (4byte)\]\[패킷 종류(2byte)\]\[Payload(0~65535byte)\]

맨 앞의 MagicByte는 패킷 자체가 유효한지 검증하는 바이트로 고정된 값을 가짐\
> p.s. MagicByte는 이후 5차에서 만들어진 것. 기록을 나중에 써서 깜빡함

전체 길이가 아닌 Payload의 길이를 세고 있는데, 이는 현재 패킷의 구조가 복잡하지도 않고 헤더도 크기가 고정적이었기 때문임\
나중에 헤더가 복잡해질 것 같다면 TCP 헤더 구조와 비슷하게 전체 길이와 헤더 길이를 알리는 공간이 생길 것으로 보임

> p.p.s. 사실 Sample4로 만들어본지는 꽤 됐는데 깜빡해서 5차 작성하며 같이 작성함..

### 5차 - 바이트 기반 통신과 패킷, 연결, 상태 제어

직접 객체를 바이트로 변환하고 스트림에 보낸 뒤 그걸 객체로 변환해서 사용하는 흐름을 만들어봤다!

클라이언트와 서버가 같이 사용하는 코드가 너무 많아 `Protocol` 클래스 라이브러리 만들었고,\
패킷 종류와 Payload, 객체 -> byte 배열로, byte 배열 -> 객체로 바꾸는 로직을 한 곳에 모아 둠

이를 통해 정말 쉽게 보낼 데이터를 4차에서 정의한 규격으로 소통할 수 있는 바이트 배열을 만들거나\
읽어들인 바이트를 객체로 변환하는 동작을 서버와 클라이언트 모두 동일하게 구성할 수 있었음

`ReadExactlyAsync`로 한 번에 읽는 바이트 수를 보장했고,\
MagicByte => Payload Length => Payload Type => Payload 순으로 읽는 하나의 파이프라인을 만들어 일관된 동작을 하도록 만듬

연결 직후 바로 채팅하는 대신 서버가 클라이언트에게 사용자 이름을 먼저 요청하고,\
클라이언트가 이름을 보내면 클라어언트의 UUID와 방 목록을 돌려주는 과정을 추가함

원래 나중에 구현하려고 했던 방 기믹을 이번에 추가하기도 함

클라이언트는 연결 후 이름 작성 시 바로 특수한 방인 lobby에 들어가게 되고,\
서버에게서 사용자의 임시 번호인 `roomUserId`를 부여받으며, 동시에 유저 리스트를 받아 번호와 이름을 서로 매핑하게 만듦\
이 매핑한 정보를 토대로 Broadcast와 `/msg` 명령어를 통한 귓말까지 구현함

이렇게 단순 문열이 아닌 직접 정한 패킷 규격을 통해 사용자 정보와 요청, 채팅 메세지가 오가는 것을 검증함

다만 새로운 방 생성 및 입장/퇴장, 잘못된 패킷 처리, 자원 처리 등 미흡한 부분이 존재하여 Unity 클라이언트를 만들어보기 전에 이 부분들을 체크하고 넘어갈 예정임
